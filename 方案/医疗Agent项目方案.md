# 慧医助手（MediAgent）—— 智能医疗多 Agent 平台设计方案

> 项目定位：面向医院门诊与院后场景的 **对话式医疗多 Agent 平台**，采用「主 Agent 负责聊天引导 + 子 Agent 负责具体诊疗业务并回传结果」的编排架构，覆盖 **智能门诊分诊、智能病历辅助生成（语音输入）、智能院后随访管理、智能心理分级评估** 四大核心功能，医学影像辅助诊断一期降级为「报告文本智能解读」，真正读片列入二期。
>
> 参考依据：国家卫健委《卫生健康行业"人工智能+"应用场景参考指引》（对应大模型项目分析 PPT 第 11 页）。
>
> 技术底座（贴合本人已有经验）：Python + LangChain/LangGraph + 通义千问 Qwen 大模型 + 本地 Ollama 小模型 + Redis 会话管理 + 自定义 Tool 调用。
>
> **本人角色：项目参与成员（大模型应用工程师），在技术组长确定的整体架构下，负责其中若干功能模块。**

## 一、项目概述

### 1.1 一句话定位
一个部署在**医院内网预研/演示环境**、由**主控 Agent 统一对话交互、多个子 Agent 分头执行诊疗业务并回传结构化结果**的医疗辅助平台，医生和患者通过统一聊天入口即可完成导诊、病历书写、院后随访、心理评估等高频日常事务。

> 说明：本项目当前处于 **PoC / 预研验证阶段**，尚未正式接入医院 HIS/EMR 生产系统。受医疗数据与合规限制，验证过程使用**脱敏数据与公开数据模拟**，未使用真实患者病历。

### 1.2 要解决的痛点

| 场景 | 现状痛点 | 本平台解法 |
|---|---|---|
| 门诊导诊 | 高峰期导诊台排队，患者自述不清、挂错科室 | 对话式分诊 Agent，几轮问询推荐科室并给就诊指引 |
| 病历书写 | 医生"小时级"手写病历，占用大量接诊时间 | 语音输入 + 结构化生成，缩至"分钟级"，且符合文书规范 |
| 院后随访 | 出院患者随访靠人工电话，遗漏多、成本高 | 随访 Agent 定时自动回访、用药提醒、异常转人工 |
| 心理评估 | 量表发放/计分靠人工，标准不统一 | 量表 Agent 自动引导作答、规则打分、分级建议 |
| 报告解读 | 患者看不懂影像/检验报告 | 报告解读 Agent 用通俗语言解释（一期文本层面） |

### 1.3 一期 / 二期边界（控制复杂度）

- **一期（本方案落地范围）**：智能门诊分诊、智能病历辅助生成（语音）、智能院后随访、智能心理分级评估、报告文本解读。
- **二期（规划，暂不实现）**：真实医学影像读片（需专病模型 + 影像数据标注 + 对接 PACS）、电子病历内涵质控、接入 HIS/EMR 全流程。

## 二、系统总体架构

### 2.1 多 Agent 协作架构

采用 **「1 个主 Agent + 4 个子 Agent」** 的主从（Supervisor）编排模式（整体架构由技术组长设计）：

```
                    ┌─────────────────────────────┐
                    │         用户 / 医生           │
                    │    （Web 聊天窗 / 语音录入）    │
                    └──────────────┬──────────────┘
                                   │ 文本 / 语音(ASR 转文字)
                                   ▼
                    ┌─────────────────────────────┐
                    │    主 Agent：MediGate        │
                    │  · 意图识别 / 任务路由         │
                    │  · 多轮对话引导与追问          │
                    │  · 汇总子 Agent 结果并回传      │
                    │  · 会话状态维护（Redis）       │
                    └──────┬───────────┬───────────┘
                           │ 结构化指令下发
           ┌───────────────┼───────────┼───────────────┐
           ▼               ▼           ▼               ▼
   ┌──────────────┐ ┌─────────────┐ ┌─────────────┐ ┌──────────────┐
   │ 分诊 Agent    │ │ 病历生成     │ │ 随访 Agent   │ │ 心理评估      │
   │ TriageAgent  │ │ RecordAgent │ │ Followup    │ │ PsychAgent   │
   │              │ │             │ │  Agent      │ │              │
   │ 对话式问诊   │ │ ASR语音转写  │ │ 定时回访    │ │ 量表引导作答 │
   │ 科室推荐     │ │ 结构化病历   │ │ 用药提醒    │ │ 规则分级打分 │
   │ 就诊指引     │ │ 文书规范校验 │ │ 异常预警    │ │ 评估报告生成 │
   └──────┬───────┘ └──────┬──────┘ └──────┬──────┘ └──────┬───────┘
          └────────────────┼──────────────┼────────────────┘
                           │ 结构化 JSON 结果回传
                           ▼
                    ┌─────────────────────────────┐
                    │       MediGate（主 Agent）    │
                    │   二次汇总 → 自然语言 / 文书    │
                    └──────────────┬──────────────┘
                                   ▼
                            展示给用户 / 医生
```

**协作机制说明：**
1. **意图识别**：主 Agent 对用户输入做意图分类，映射到「分诊 / 病历 / 随访 / 心理评估 / 报告解读 / 闲聊」之一。
2. **路由下发**：主 Agent 把任务连同上下文化成一条结构化指令，交给对应子 Agent。
3. **子 Agent 执行**：子 Agent 是带专属工具（Tool）的 LangChain Agent，独立完成"调工具 → 整理 → 输出结构化 JSON"。
4. **结果回传**：子 Agent 只回传**结构化 JSON**（如科室 + 置信度 + 理由），不直接面向用户；由主 Agent 二次加工成自然语言或标准文书，保证对话语气统一、可读性好。
5. **状态兜底**：整个过程由 Redis 维护会话状态与上下文，超出预算自动压缩摘要（复用本人"小模型压缩"经验），避免上下文无限膨胀。

### 2.2 技术栈总览

| 层次 | 选型 | 说明 |
|---|---|---|
| Agent 编排 | **LangChain + LangGraph（StateGraph）** | 主从多 Agent、状态机流转、工具调用 |
| 主模型 | **通义千问 Qwen 系列**（远程 API，兼容 OpenAI 协议） | 复杂推理、对话、文书生成 |
| 轻量模型 | **本地 Ollama `qwen2.5:1.5b/7b`** | 高频轻量任务：意图初筛、上下文摘要压缩、简单分类（0 成本） |
| 语音识别 ASR | 阿里云 Paraformer / 本地 Whisper | 语音输入转文字（医疗场景优先国产 Paraformer） |
| 会话/缓存 | **Redis**（含 Redis Stack 向量检索能力） | 会话状态、上下文压缩缓存、随访任务队列 |
| 持久化 | MySQL / PostgreSQL | 病历、随访记录、心理量表结果 |
| 知识库/RAG | Faiss / Redis 向量 | 科室导诊知识、随访话术库、量表题库 |
| 后端 | FastAPI | 提供 REST 接口、WebSocket 流式对话 |
| 前端 | Vue3（医生工作站） + Streamlit（内部原型） | 对话界面 / 语音录入 / 医生复核面板 |
| 部署 | Docker + Nginx，内网预研/演示环境 | 验证阶段，未接入生产系统 |

## 三、各 Agent 详细设计

### 3.1 主 Agent：MediGate（对话总控 + 路由）

**职责**：用户统一入口；负责意图识别、多轮追问、路由下发、结果汇总呈现。

- **输入**：用户/医生的自然语言文本，或语音经 ASR 转写后的文本。
- **核心逻辑**：
  1. **意图分类**：先用本地小模型做一次粗分类（省 token），置信度低时再回退大模型精判。
  2. **槽位补齐**：分诊需要"症状、持续时间、年龄、既往史"，病历需要"主诉、现病史、既往史、过敏史"，缺哪个就追问哪个（多轮）。
  3. **路由**：槽位齐全后下发子 Agent。
  4. **汇总**：接收子 Agent 的结构化 JSON，套用统一话术模板转成自然语言/标准文书。
- **关键设计点**：主 Agent 不直接碰医疗业务规则，只做"理解 + 协调 + 表达"，保证职责单一、易维护。

### 3.2 分诊 Agent：TriageAgent（智能门诊分诊）

对应 PPT 第 12 页"数字人对话式导诊"。

- **功能**：根据患者主诉自动推荐诊疗科室 + 就诊指引 + 挂号建议。
- **实现**：
  - RAG 检索「科室导诊知识库」（症状 → 科室映射，来源为医院官方导诊手册）。
  - 大模型对症状做归一化 + 鉴别（如"胸痛"需区分心内科 / 呼吸科 / 急诊）。
  - 输出结构化结果：`{ 推荐科室, 备选科室, 置信度, 就诊建议, 是否建议急诊 }`。
- **工具**：`search_dept_kb(query)`（向量检索）、`query_registration(科室)`（挂号余号，可选）。

### 3.3 病历生成 Agent：RecordAgent（智能病历辅助生成·语音输入）

对应 PPT 第 13、14 页"语音病历生成 / 甲级病历文书"。

- **功能**：医生口述（语音）→ ASR 转写 → 结构化病历生成 → 规范校验 → 医生复核确认。
- **流程**：
  1. 医生语音 → Paraformer ASR 转文字。
  2. 大模型按「主诉 / 现病史 / 既往史 / 过敏史 / 体格检查 / 诊断 / 处理意见」字段抽取并生成结构化病历。
  3. 规则校验器检查必填字段、时限性、术语规范性（甲级病历要求）。
  4. 医生在复核面板确认/修改后落库。
- **工具**：`asr_transcribe(audio)`、`validate_record(json)`（规则校验）、`save_record(json)`。
- **安全设计**：病历**必须医生人工确认**才生效，AI 只做"草稿"，规避大模型幻觉风险。

### 3.4 随访 Agent：FollowupAgent（智能院后管理）

对应清单"智能患者院后管理 / 智能随访"。

- **功能**：出院患者自动定时随访、用药提醒、康复指导、异常预警转人工。
- **实现**：
  - Redis 延迟队列 + 定时任务（Celery/APScheduler）触发随访。
  - 大模型按随访计划生成个性化回访问卷（依病种、术式）。
  - 收集患者反馈 → 规则判断异常（如疼痛加剧、发热）→ 触发预警给责任医生。
- **工具**：`create_followup_task(patient, plan)`、`send_reminder(patient)`、`alert_doctor(patient, reason)`。
- **输出**：结构化随访记录 + 风险等级。

### 3.5 心理评估 Agent：PsychAgent（智能心理分级评估）

对应清单"智能心理分级评估与护理"。

- **功能**：引导患者在线完成标准化量表（GAD-7 焦虑、PHQ-9 抑郁、PSQI 睡眠等），规则打分 + 分级 + 护理建议。
- **实现**：
  - 量表题库（RAG 或固定配置）逐题引导作答。
  - **规则引擎打分**（量表有明确计分标准，不依赖 LLM 打分，避免漂移）。
  - 大模型仅用于生成"分级解读 + 人文关怀 + 就医/护理建议"。
  - 输出：`{ 量表名, 总分, 分级(无/轻/中/重), 建议, 是否建议转诊心理科 }`。
- **工具**：`get_scale(scale_name)`、`score_scale(answers)`（纯规则）、`gen_advice(score, level)`。

### 3.6 报告解读 Agent（一期轻量，可选）

对应 PPT 第 19 页"拍一拍报告解读"。

- **功能**：患者拍照/上传检验或影像**报告文本**，用通俗语言解释指标含义 + 异常项提示。
- **一期范围**：仅处理"报告文本 + 检验指标"，用 OCR + 大模型解释；**不做真实影像读片**（明确列二期）。

## 四、技术选型与设备合理性分析

### 4.1 硬件设备清单

| 设备 | 配置 | 用途 | 数量 |
|---|---|---|---|
| 开发工作站 | 普通 PC，32GB 内存 + 无/单 GPU | 日常开发、跑本地 Ollama 小模型调试 | 4（每人一台） |
| 预研/演示服务器 | 32 核 CPU + 64GB 内存 + 可选 NVIDIA L4(24GB) | 部署全链路、演示、内部验证 | 1 |

> 验证阶段无需生产级双机高可用，单台预研服务器即可，后续正式上线再扩容。

### 4.2 模型与推理部署合理性分析

这是本方案最关键的工程取舍，核心原则是 **"高频轻量任务本地化、低频复杂任务上大模型"**，最大化性价比：

| 环节 | 用什么 | 为什么 |
|---|---|---|
| 意图初筛 / 上下文压缩（高频） | 本地 Ollama `qwen2.5:1.5b/7b` | 任务简单、调用频繁，本地跑 **0 API 成本**，且延迟低（复用本人已验证经验） |
| 复杂推理 / 文书生成（低频） | 远程 Qwen 系列 API | 只有真正需要强推理时才调大模型，控制积分/费用 |
| ASR 语音转写 | 阿里云 Paraformer API 或本地 Whisper | 医疗术语识别好；若数据敏感则本地部署 Whisper |
| 心理量表打分 | 纯规则引擎（Python） | 量表有权威计分标准，**不交给 LLM 打分**，保证稳定可解释 |

**为什么不需要训练大模型 / 不需要大 GPU 集群：**
- 本项目全部基于**提示工程（Prompt）+ RAG + 工具编排（Tool）**实现，不涉及模型微调，因此**无需 A100/A800 级训练卡**。
- 一期主模型走远程 API，本地仅需一张 L4 甚至纯 CPU 即可跑 1.5b/7b 小模型，硬件投入低、上线快。

### 4.3 数据与合规（医疗场景硬约束）

- **数据来源受限**：验证阶段**无真实病历数据**，使用**脱敏数据与公开数据集模拟**，未接入医院生产库。
- **私有化部署（预研环境）**：系统部署在内网，患者数据、录音不出院。
- **脱敏**：日志与调试数据做去标识化处理。
- **人工复核闭环**：病历生成、分级建议等关键输出必须有医生确认环节，AI 定位为"辅助"而非"替代"。
- **权限分级**：医生 / 患者 / 管理员角色隔离，病历访问需授权。

### 6.2 我（参与成员）负责的工作

本人在技术组长确定的整体架构下，**深度负责其中 3 个模块**，其余为配合：

1. **Redis 多轮会话管理与上下文压缩**：设计多轮对话状态存储；上下文超预算时用本地小模型生成摘要压缩（区分"最近轮原文保留 + 历史摘要化"），解决 token 膨胀（本人最核心、投入最多的模块）。
2. **病历生成与心理评估两个子 Agent 的工具（Tool）与 Prompt 开发**：用 `@tool` 封装 `asr_transcribe / validate_record / score_scale` 等工具，编写系统提示词，打通 LLM 与外部系统的调用闭环。
3. **ASR 语音接入**：集成语音转写服务，打通"语音 → 文本 → 结构化病历"链路，并处理医学术语转写准确率问题。
4. （配合）参与 LangGraph 编排联调、意图分类的成本优化讨论，协助后端接口联调。

### 6.3 实际工作摩擦与协作（真实场景）

- 医疗顾问**多次调整病历模板与量表条目**，导致对应 Prompt 与工具字段反复返工。
- 后端接口字段定义与前端/Agent 对不齐，联调阶段**多次返工修正**。
- 模型 API 有配额限制，调试阶段需**控制大模型调用频次**（复用本地小模型做高频验证）。
- 无真实病历数据，全程用脱敏/公开数据验证，效果与真实场景存在差距（已诚实记录在第八节）。

## 七、部署方案

```
医院内网 · 预研/演示环境
┌──────────────────────────────────────────────┐
│  Nginx（反向代理 / 统一入口）                  │
│        │                                       │
│  FastAPI 应用容器（Agent 服务）                 │
│        │                                       │
│  ├── Redis（会话 / 队列 / 向量）               │
│  ├── MySQL（病历 / 随访 / 量表）               │
│  ├── Ollama 本地小模型服务（意图/压缩）          │
│  └── 远程 Qwen API（内网出口，可选）            │
└──────────────────────────────────────────────┘
```

- 全链路 Docker Compose 一键部署，Nginx 统一入口。
- 验证阶段单台预研服务器即可；正式上线需升级为生产高可用并完成医院合规审批。
- 若医院要求**完全离线**，可将主模型替换为**私有化部署的 Qwen2.5-14B/72B**（需相应 GPU），架构不变、仅替换推理后端。
- 接口全部走 REST + WebSocket（流式输出），便于医生工作站/患者端复用。

## 九、已知缺陷与可优化点（诚实记录，简历加分项）

> 使用/开发过程中实际暴露的问题，用于体现复盘能力与工程思考。

1. **分诊误判风险**：依赖导诊知识库覆盖度，罕见/复合症状（如"胸痛 + 心慌 + 胃不适"）易误判科室。→ 优化：引入更多真实病例做 Few-shot，加"鉴别追问"，低置信度转人工导诊。
2. **病历生成的医学事实准确性**：大模型存在幻觉，可能编造不存在的检查结果/诊断。→ 已强制"医生复核才生效"；后续可加"事实一致性校验"与术语库约束。
3. **ASR 医学术语/方言识别率低**：专业术语、口音、嘈杂环境转写错误多。→ 优化：接入医疗领域 ASR 热词表，支持医生录音后手动纠错。
4. **心理量表 LLM 打分与规则不一致**：若让 LLM 参与打分会出现漂移。→ 已改为**纯规则计分**，LLM 仅生成解读建议，两者职责分离。
5. **上下文压缩可能丢失关键信息**：摘要化历史时可能漏掉"过敏史、既往手术"等关键字段。→ 优化：关键医学字段单独结构化存储，不参与摘要压缩。
6. **多 Agent 结构化 JSON 丢失细节**：子 Agent 回传 JSON 时，口语化的 nuance 与上下文信息会丢失。→ 优化：协议中保留"原始关键句 + 结构化字段"双通道。
7. **未接入 HIS/PACS**：病历、报告需手动导入导出，无法与院内系统全流程打通。→ 列为二期重点。
8. **医学影像真实读片未实现**：一期仅做报告文本解读，未对影像图像本身建模。→ 二期需专病模型 + 影像数据标注 + PACS 对接，超出当前范围。
9. **数据与合规限制**：验证全程无真实病历数据，效果与真实场景存在差距。→ 正式落地需医院数据授权 + 合规审批。
